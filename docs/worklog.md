## 〇、貫穿全程的三條規則

使用者定的，每一條都是踩過之後才立的：

   覆蓋掉他在 App 裡改的東西。

## 二、幾個關鍵決定，以及理由

### 2.1 描圖：從像素改成幾何（08-13）

原本是對掃描圖做像素分析。承認它到極限之後改用 CAD 圖 `IMG_0197`，對線段做幾何。

**最關鍵的一句話是 `c2a2ee0`：一道牆的兩條線是它的兩個面，不是兩道牆。**
CAD 圖上牆是一對相距 15–17px 的平行線。把它們當成兩道牆，房間會多出一堆
不存在的隔間；取其中一條當中心線，整張圖會系統性偏移半個牆厚。正解是**取那對線
的中心**。格線改成中心線之後，牆位置的中位數誤差從 5.9cm 掉到 0.5cm。

使用者定的兩條規則寫成了會跑的檢查（`scripts/check-0199.mjs`），不是只寫在文件裡。

### 2.2 材質：procedural 與實掃是兩種東西（08-14～15）

第一版挑的是 ambientCG，使用者說「這個有些簡陋」。查下去發現關鍵欄位是
`creationMethod`：ambientCG 有 1412 個 **PBRProcedural**、只有 351 個
**PBRPhotogrammetry**，我挑到的大多是前者。**簡陋不是解析度問題，是那張圖本來就是
程式生成的**——它每一格都一樣，實掃的每一平方公分都不同。

改用 Poly Haven（全站攝影測量、全 CC0）之後就對了。

**拉絲金屬是 procedural 合理的少數例外**：它本來就是機械加工的規則紋理。

### 2.3 家具：風格只能靠件數做（08-19）

使用者要「多找幾種風格，我全部都要」。**一把椅子沒有風格參數——它就是被掃下來的
那一把。** 所以彩繪鄉村、工業、古典、中式、金屬，只能一類抓一件實掃。這是目錄從
94 長到 127 件的原因，也是 models/ 會膨脹到 41MB 的原因。

目錄尺寸**一律讀模型 POSITION accessor 的 min/max**，不估。

### 2.4 櫃體從 Kenney 搬回 Poly Haven（08-19）

Kenney Furniture Kit 完全沒有貼圖，只有純色材質。我先做的是 `dressKenney()`：
按材質名字（`wood` `metal` `carpet` `glass`）套上對應的掃描圖。**這對家電有效，
對櫃體無效**——平鋪的材質貼在低多邊形上永遠長不成烘焙貼圖的樣子。並排渲一張就
看得出來：一邊是均勻淺米色配均勻細紋，一邊有深淺變化、磨損與包漿。

所以櫃體六件全部改用 Poly Haven 實掃。Kenney 現在只留「圖庫真的沒有實掃版本」的
家電與衛浴——冰箱、爐具、洗衣機、馬桶、浴缸，那些沒有人拿去掃。

### 2.5 models/ 退出 repo（08-19）

41MB 進 git 的代價是**每個 clone 都要付**，而它不是每個人都需要。所以
`.gitignore` 擋掉整個目錄，改成 `npm run assets` 自己抓。

**貼圖那 10MB 留著**：牆、地板、每一個表面都要用，不存在「有需要的人」這種區分。

改寫歷史把 39.6MB 從所有 commit 移掉（`git filter-repo`），新 clone 的 `.git`
從 55MB 降到 19MB，170 個 commit 一個沒少。做之前備份了 bundle 與整個 `.git`，
做完比對舊 / 新 HEAD 的檔案清單與 `client/src` 的 tree hash，確認除了 models
之外一個 byte 都沒動。

> **其他機器要處理**：SHA 全變了，`git pull` 會失敗。要跑
> `git fetch origin && git reset --hard origin/master`（有改動先 stash）。

### 2.6 一把椅子沒有風格參數，一個衣櫃有（08-19）

使用者說「不可能只有一款衣櫃對吧」。查下去發現**真的只有一款**：Poly Haven 全站
26 件櫃體用掉 22，沒有任何一件是衣櫃（現在那個是 `vintage_cabinet_01` 頂替的），
ambientCG 的 300 個模型裡家具 0 件。攝影測量給的是「誰剛好掃了什麼」。

所以分兩條路，而**分界線是「款式差在哪裡」**：

- **差在正面 → 自己蓋。** 衣櫃的差別是對開／三門／推拉／開放／鏡面／頂櫃，全在
  正面，而正面是平的。參數化 14 款，貼同一批實掃木皮，跟掃描模型同一個世界。
- **差在造型 → 去下載。** 沙發、床、椅子的差別是整個輪廓，那個參數化不出來。
  Quaternius（CC0）是成套的，Closet/ShortCloset、BedDouble/BedTwin/King、十二款
  沙發——正是實掃圖庫給不了的「同一樣好幾款」。

**這個來源有一條規則跟 Poly Haven 相反，寫在腳本開頭：模型尺寸不是真實尺寸。**
實掃是量出來的，所以它自己的包圍盒就是真相；Quaternius 是照遊戲比例做的，衣櫃在
模型單位裡 2.98 高、雙人床 4.26 長，大約兩倍。這裡的目錄尺寸要**照真實家具填**。
把兩條規則搞混，就是 180cm 廚櫃渲成 54cm 那個坑的反面。

### 2.7 「全部貼皮」要先能被驗，才有資格說做完了（08-19）

這句話我講錯過三次，每次成因一樣：抽樣看幾件、有紋理就宣布完成。所以這次先寫
`bench/verify-textures.mjs`——把目錄每一件實際建出來，走訪每個材質，列出沒有貼圖
的，連材質名字一起印。

**第一次跑出 22 件，而其中一部分是我量錯的。** `applyScan` 是非同步的：圖還沒載到
就先把材質排進佇列、之後補上。所以在物件剛建好的當下問「有沒有貼圖」是**錯的時間
點**——量到的是「還沒貼上去」，不是「沒貼」。加了 `scansPending()` 等佇列歸零，
真正的漏是 17 件。

**同樣重要的是把「刻意不貼」寫下來。** 玻璃與鏡面真的沒有紋理；上釉陶瓷貼上去等於
加髒污（兩個圖庫的 ceramic 掃描**全部都是磁磚**，含填縫與磨損）。這些列進 EXEMPT
並逐條寫理由——不在 EXEMPT 又沒有 map 的才是漏掉的。這條線畫出來，「全部」才是個
可以檢查的字，而不是一句感覺。

## 三、我判斷錯的地方

**這節是給檢閱用的重點。** 每一條都是「看起來已經好了、其實沒有」，靠的是回頭實測
才發現，不是靠推理。

### 3.1 縮圖會騙人

挑貼圖時看縮圖選了五張，渲出來才發現全錯：`WoodFloor048` 是黑的、`Concrete034`
是白的、`Carpet014` 完全沒起伏、`Fabric012` 是海軍藍。名字也會騙人——
`american_walnut_veneer`、`natural_walnut_veneer`、`mocha_oak_veneer` 掃出來
**全是灰的**。

**規則：判斷一張貼圖的明度，看渲染結果或直接看 Diffuse 圖，永遠不要看縮圖。**

### 3.2 「94 件全部有模型」是錯的

`fetch_models.py` 從頭重建 manifest，把 `fetch_kenney.py` 併進去的 **21 筆抹掉**。
那 21 件（衣櫃、冰箱、馬桶、浴缸、床）安靜地退回程式生成的方塊——`.glb` 還在磁碟上、
面板預覽圖也還在，**從外面完全看不出來**，因為 `loadFurnitureModel` 找不到條目
只會回 `false`。

修法有三層：抓取腳本改成**合併**而不是重建、`done()` 要求 manifest 有那一列、
`bench/furniture.mjs` 加一個對照檢查（少一筆就 throw）。

**教訓：一個「失敗時安靜退回合理結果」的設計，必須配一個外部檢查。**

### 3.3 等比縮放讓 19 件比它宣告的小

模型用 `min(kx, kz)` 等比縮放，於是長寬比跟目錄不同的就填不滿。實測 94 件裡有
19 件渲出來比宣告尺寸矮 10cm 以上，最糟的是 180cm 的廚櫃**渲成 54cm**。改成逐軸。

同一支還有 `inst.scale.y = ` 應該是 `*=`。這個在所有 scale 都還是 1 的時候完全
看不出來，直到 200cm 的衣櫃渲成 83cm。

### 3.4 驗證腳本自己是錯的

- `verify-stretch.mjs` 第一版是**恆真式**：算的是 `nx * (w/nx)`，恆等於 `w`。
  它永遠會通過。重寫成量真實的世界包圍盒。
- `verify-deeplink.mjs` 一直失敗，因為它斷言在 `img9720` 上——那個方案使用者早就
  刪了。改成跟後端自己那份比。

**驗證腳本要先證明它會失敗，再相信它通過。**

### 3.5 虛線門框查了兩次錯方向

先猜共面 z-fighting，再猜陰影／GTAO，都不是。真正原因是**整個 3D 根本沒有反鋸齒**：
`antialias: true` 只作用在預設 framebuffer，而畫面走的是 EffectComposer 的離屏
target，它的 `samples` 預設是 0。

補完之後才發現還有兩條路徑沒被覆蓋：全景拍攝走 CubeCamera 繞過 composer、
glTF 模型的貼圖 anisotropy 是 1（專案自己蓋的都是 8）。

### 3.6 `loading="lazy"` 讓 72 個按鈕換上 0 張圖

面板是一條長清單，懶載入之下離開視窗的那些永遠不發請求、`onload` 也永遠不觸發。
**而且不會有 404 之類的線索**。拿掉就好，72 張小圖總共約 1MB。

### 3.7 `dressKenney` 第一版沒有任何效果

我把 roughness 設在 `applyScan` **之前**，而 `applyScan` 會強制 `roughness = 1`；
而且沒有取掃描圖的顏色。使用者問「是沒有還是你沒看到」——是我沒有單獨驗證它。

### 3.8 環境問題被誤判成程式 bug

Playwright 逾時其實是機器負載加上軟體光柵化。另外 `| head -3` 造成 SIGPIPE 把
指令殺掉，看起來像跑失敗。

### 3.9 用檔名分風格，79/127 掉進「現代」

風格篩選第一版是按檔名與資產名正則分類的。結果「現代」變成垃圾桶：拱形雕花立鏡、
六臂銅吊燈、搖椅、兩張絨面切斯特菲爾德全在裡面。原因是**檔名兩個方向都會騙**——
`modern_coffee_table_02` 真的是現代，但 `sofa_01` `sofa_02` `sofa_03` 分別是雕花
長椅、絨面切斯特菲爾德、捲臂皮沙發，三個世紀擠在三個連號裡。

**會騙人的篩選比沒有篩選更糟**：使用者按了「現代」拿到一張搖椅，之後就不會再信
那排按鈕。做法改成拉一張縮圖對照表逐件看圖重判，27 件改掉。跟 3.1 是同一條教訓的
另一半——縮圖會騙人，檔名也會，但**渲出來的圖不會**。

### 3.10 一個檔案失敗就 break，看起來像整包被鎖死

Quaternius 走 Google Drive，會限流。第一版的下載迴圈遇到例外就 `break`，而失敗的
通常是排在前面的 `.mtl`——於是每一次執行都停在同一個檔上，後面四十幾個 `.obj`
一次都沒被試過。表面症狀是「Drive 把整包鎖死了」，實際是我自己不再問。改成逐檔
重試三次、失敗就跳過下一個。

（`.mtl` 不能省：少了它 trimesh 讀出來的 geometry 名字會變成 `Cube_1`，而語意化的
材質名正是 `dressFlat()` 掛實掃圖的依據。）

### 3.11 後面的程式把前面的 onclick 蓋掉了

家具面板的分類標題自己有一個處理器（存摺疊狀態、重跑篩選）。但 `wireTopbar()` 在
`buildCatalog()` 之後跑，對**所有** `.panel-title.collapsible` 重設 `onclick`，
把它整個蓋掉。外觀完全正常——class 照樣 toggle、CSS 照樣把下一個 div 收起來——
只是狀態不再被記住、篩選也不再更新。

肉眼看不出來，`bench/verify-palette.mjs` 的「重載後摺疊還記得」當場抓到。

### 3.12 在非同步貼圖落地之前就去量它

見 2.7。稽核腳本第一版量到 22 件沒貼皮，其中 5 件其實貼了、只是還在下載。
**一份混著「真漏」與「還沒到」的清單，比沒有清單更浪費時間**——它會讓人去修
根本沒壞的東西。修法是讓 `textures3d.ts` 露出 `scansPending()`，稽核等它歸零。

### 3.14 兩個「不會報錯的沒貼皮」

稽核擴大到 Quaternius 之後又抓到兩個，兩個都不會有任何錯誤訊息：

- **材質名不在材質上。** Kenney 的 glTF 帶材質名，Quaternius 走 OBJ → trimesh →
  GLB，名字掉到 node 上。`dressFlat` 只比對 `m.name`，於是整個來源一件都對不上。
- **`/light/` 匹配到 `LightOrange`。** Quaternius 用顏色命名材質，而燈具原型刻意
  不貼圖，所以那兩張地毯永遠純色。加 `\b` 詞界。

還有一件更值得記：**前一批那 10 件 Quaternius 從來沒被稽核過。** 它們在 manifest
裡、模型也在磁碟上，但沒有目錄列，而稽核是照目錄跑的。「驗過了」的前提是「它在
被驗的集合裡」。

### 3.13 我把自己的路徑 bug 當成 Google Drive 在限流

Quaternius 抓了兩輪、每輪一小時，快取始終停在 13 個檔，我兩次都把結論寫成
「Drive 對這個 IP 限流」，還寫進了 commit message 與工作紀錄。

**真正的原因是 `gdown` 回傳的 `path` 是相對於當前工作目錄的，不是相對於我傳的
`output=`。** 於是檔案下載成功、但落在 repo 根目錄的 `OBJ/`，而讀取端只看
`.cache/quaternius/<pack>/OBJ/`——每一輪都以為自己什麼都沒拿到，然後重抓。
發現它是因為 commit 前掃 `git status`，看到一個沒人放的 `OBJ/`，裡面 30 個檔。

限流確實也存在（`FileURLRetrievalError` 是真的），**但那不是主因**，而我讓那個
真訊號蓋掉了自己的錯。教訓不是「要更懷疑外部服務」，是**外部服務給了一個合理的
失敗理由時，那個理由會讓人停止檢查自己那一側**。

## 四、驗證工具

`bench/` 底下全部是 headless Chromium 實測，不是單元測試。

| 工具 | 驗什麼 |
|---|---|
| `verify-esc.mjs` | Esc 在每個檢視都要取消；在輸入框裡要兩下 |
| `verify-stretch.mjs` | 家具在 3D 的**真實包圍盒**等於宣告的 w/h，拉伸要跟著變 |
| `verify-rooms.mjs` | 沒有兩塊房間地板佔同一塊地 |
| `verify-wall.mjs` | 牆編輯的端到端 |
| `verify-deeplink.mjs` | `?plan=<id>` 對真的後端 |
| `verify-partition.mjs` | 隔間線端到端 |
| `verify-flicker.mjs` | 繞著轉，看有沒有閃爍 |
| `furniture.mjs` | 全目錄排一間房渲一張，外加 manifest 對照 |
| `verify-palette.mjs` | 面板：搜尋 ∩ 風格、複選是聯集、摺疊不改變篩選、重載記得 |
| `thumbs.mjs` | 幫沒附預覽圖的模型渲一張（獨立 three.js 頁，透明背景） |
| `verify-textures.mjs` | 每一件的每一個材質都要有貼圖；刻意留白的列 EXEMPT 並寫理由 |
| `soak.mjs` / `report.mjs` | 長跑，看有沒有漂移 |
| `coldstart.mjs` / `drag.mjs` | 首幀成本、一次拖曳幾次重繪 |

`scripts/` 底下：`check-0199.mjs`（使用者兩條規則的檢查）、`trace-0199.mjs`（描圖）、
`solid-columns.mjs`（既有方案的柱子轉換，預設 dry-run）、`fetch_*.py`（素材）。
